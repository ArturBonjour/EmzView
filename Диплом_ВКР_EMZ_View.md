# Введение

**Актуальность темы исследования.** Цифровая трансформация индустрии развлечений привела к беспрецедентному росту объема доступного видеоконтента. По данным аналитического агентства Statista, к 2024 году совокупные библиотеки глобальных потоковых сервисов (Netflix, Amazon Prime Video, Disney+, Kinopoisk HD и др.) превысили 1,5 миллиона наименований фильмов и сериалов [21]. Российский рынок онлайн-кинотеатров демонстрирует ежегодный рост на 25--30%, при этом объем платной выручки в 2023 году составил более 70 млрд рублей [5].

В условиях подобного информационного изобилия стандартные механизмы поиска и фильтрации (по жанру, году выпуска, рейтингу) перестают эффективно решать задачу помощи пользователю. Исследования в области когнитивной психологии фиксируют феномен «паралича выбора» (англ. choice overload): при наличии избыточного числа альтернатив пользователь тратит на выбор несоразмерно много времени, испытывает неудовлетворенность и с высокой вероятностью покидает платформу без целевого действия [4]. По оценкам компании Netflix, внедрение персонализированных рекомендаций позволило сократить показатель отказов (churn rate) на 25% и сэкономить более 1 млрд долларов в год благодаря удержанию подписчиков [14].

Актуальность темы усиливается тем, что современные пользователи взаимодействуют с контентом через множество каналов: десктопный браузер, мобильное приложение, телевизионные приставки, мессенджеры. Мультиплатформенность порождает новые инженерные вызовы: необходимо обеспечить единый профиль предпочтений и непрерывный пользовательский опыт независимо от канала доступа [6].

**Степень разработанности темы.** Теоретическая база рекомендательных систем подробно освещена в фундаментальных работах Риччи, Рокача и Шапиры [14], а также в масштабном обзоре Бобадильи и соавторов, охватывающем более 200 публикаций [7]. Методы матричной факторизации для коллаборативной фильтрации систематизированы в классической работе Корена, Белла и Волинского [12], где показано, что SVD-разложение позволяет выявить латентные факторы предпочтений пользователей. Коллаборативная фильтрация с неявными сигналами (просмотры без явных оценок) исследована в работе Ху, Корена и Волинского [11].

Контентная фильтрация на основе TF-IDF и косинусного сходства рассмотрена в работах по информационному поиску [2]. Методы коллаборативной фильтрации на основе матричной факторизации систематизированы в работе Корена и соавторов [12]; современные сравнительные оценки качества факторизационных моделей на актуальных бенчмарках представлены в работе Zhang и соавторов [15]. Алгоритм MMR (Maximal Marginal Relevance), применяемый для улучшения разнообразия выдачи, был предложен Карбонеллом и Голдштейном [8] и успешно адаптирован к задачам рекомендаций в последующих исследованиях.

Вопросы объяснимости рекомендаций (explainable recommendations) активно исследуются в последние годы [5]; доказано, что понимание причин рекомендации повышает доверие пользователей и конверсию. Вместе с тем вопросы интеграции нескольких стратегий рекомендаций (гибридный подход) в единой мультиплатформенной системе с поддержкой объяснимости выдачи и рекомендаций по эмоциональному контексту остаются недостаточно проработанными в открытых прикладных реализациях. Большинство учебных проектов ограничиваются реализацией одного метода без инфраструктуры промышленного уровня.

**Проблема исследования** состоит в противоречии между потребностью рынка в персонализированных, объяснимых и мультиплатформенных рекомендациях и недостаточной проработанностью архитектурных и алгоритмических решений для систем среднего масштаба, не имеющих ресурсов Netflix или Яндекса. Конкретно, проблема заключается в необходимости создания системы, которая:
- обеспечивает персонализированные рекомендации с первого сеанса работы (решение проблемы холодного старта через онбординг);
- предоставляет объяснимые, разнообразные рекомендации по нескольким стратегиям (For You, Because, Mood, Similar Users);
- работает в нескольких пользовательских каналах (веб-приложение и Telegram-бот) с единым профилем пользователя;
- устойчиво функционирует при частичной недоступности компонентов системы (graceful degradation).

# 1 Аналитический раздел

## 1.1 Анализ предметной области персонализированных рекомендаций

Рекомендательные системы (РС) решают задачу автоматического ранжирования множества объектов по индивидуальной полезности для конкретного пользователя. В прикладной постановке для видеосервисов это означает построение упорядоченного списка фильмов и сериалов, который снижает когнитивную нагрузку при выборе и повышает вероятность позитивной пользовательской реакции.

Жизненный цикл пользовательского взаимодействия с РС принято делить на три фазы. В начальной фазе (холодный старт) данных о пользователе недостаточно для построения индивидуального профиля. В адаптивной фазе накопленная история оценок позволяет системе корректировать рекомендации. В стабилизированной фазе профиль пользователя обретает устойчивость, и качество рекомендаций достигает плато [4].

Для предметной области кино- и сериального контента характерен ряд специфических особенностей. Во-первых, гетерогенность контента: фильмы и сериалы имеют разные паттерны потребления -- сериалы просматриваются эпизодически в течение недель, тогда как фильм завершается за один сеанс. Во-вторых, значительное влияние эмоционального контекста: пользователь может последовательно искать триллер, романтическую комедию и семейный мультфильм, в зависимости от настроения и компании. В-третьих, критическая роль объяснимости: пользователи доверяют рекомендациям значительно больше, если понимают, почему тот или иной объект им предложен [5]. В-четвертых, высокая значимость визуального UX: постер фильма является ключевым элементом интерфейса, влияющим на первичное решение об интересе. В-пятых, многоканальность взаимодействия: пользователи ожидают непрерывного опыта между веб-клиентом и мобильными мессенджерами.

## 1.2 Обзор методов построения рекомендательных систем

**Контентная фильтрация.**

Контентная фильтрация формирует рекомендации на основе признаков объектов: жанров, описаний, актерского состава, ключевых слов. Пользователь получает рекомендации, схожие с теми, что ему уже понравились. Математически задача сводится к поиску объектов с максимальным косинусным сходством с профильным вектором пользователя [6]. Основы ранжирования объектов по индивидуальной полезности подробно рассматриваются в работе Агеева [2].

Профильный вектор формируется как взвешенное среднее TF-IDF-векторов понравившихся объектов:

**p** = (1/|L|) * Σ(i ∈ L) **d_i**,

где L -- множество объектов, получивших положительную оценку, **d_i** -- TF-IDF-вектор объекта i. (1.1)

Оценка сходства между профилем и объектом-кандидатом вычисляется через косинусное расстояние:

sim(**p**, **d_j**) = (**p** · **d_j**) / (||**p**|| * ||**d_j**||) (1.2)

Преимущества контентной фильтрации: не требует большого числа пользователей, прозрачно объясняется через сходство с уже оцененными объектами, устойчива к разреженности пользовательских данных. Недостатки: риск «пузыря фильтрации» (система замыкается на похожем контенте), зависимость от полноты метаданных, слабое использование коллективного поведения.

**Коллаборативная фильтрация.**

Коллаборативная фильтрация опирается на схожесть поведения пользователей или объектов [7]. Матрично-факторизационный подход (SVD) разлагает матрицу взаимодействий R ∈ R^(m×n) как:

**R** ≈ **U** · **Σ** · **V^T**, (1.3)

где **U** ∈ R^(m×k) -- матрица скрытых факторов пользователей, **V** ∈ R^(n×k) -- матрица скрытых факторов объектов, **Σ** -- диагональная матрица сингулярных значений, k << min(m, n) -- размерность латентного пространства. Математическая основа метода подробно изложена в работе Воронцова [3].

Оценка предпочтения пользователя u к объекту i:

r̂_ui = **u_u** · **v_i^T**, (1.4)

где **u_u** = **U**[u, :] · **Σ**[:k] -- вектор латентных факторов пользователя. (1.5)

Коллаборативные алгоритмы традиционно верифицируются на наборе данных MovieLens. Современный обзор методов построения рекомендательных систем на основе графовых нейронных сетей, включая применение к задаче CF, представлен в работе Gao и соавторов [9]. Расширение в сторону неявных сигналов взаимодействия (просмотры, клики) рассматривается в работе Hu et al. [11] и обозначено как направление дальнейшего развития EMZ View (Раздел «Заключение»). Нейронные расширения матричной факторизации -- в частности, модель Neural Collaborative Filtering (NCF), заменяющая скалярное произведение нелинейным многослойным перцептроном [10], -- демонстрируют преимущества на ряде бенчмарков, однако требуют существенно большего объема обучающих данных, что делает их менее подходящими для рекомендательных систем среднего масштаба.

Преимущества: находит неожиданные рекомендации, эффективна при накопленной истории. Недостатки: проблема холодного старта, чувствительность к разреженности матрицы.

**Гибридный подход и принцип MMR.**

Гибридные системы объединяют достоинства обоих подходов [14]. В данной работе применяется переключаемая стратегия: при объеме взаимодействий менее порогового значения используется контентная фильтрация, при достижении порога подключается коллаборативная.

Для улучшения разнообразия выдачи применяется алгоритм Maximal Marginal Relevance (MMR), предложенный Carbonell и Goldstein [8]:

MMR(d_i) = λ · sim(**p**, **d_i**) -- (1 -- λ) · max(j ∈ S) sim(**d_j**, **d_i**), (1.6)

где S -- множество уже выбранных объектов, λ ∈ [0, 1] -- параметр баланса между релевантностью и новизной. При λ = 1 MMR эквивалентен ранжированию по релевантности; при λ = 0 -- максимизирует разнообразие. В данной работе используется λ = 0,7, обеспечивающее приоритет релевантности при умеренном разнообразии.

В таблице 1.1 приведено сравнение рассмотренных подходов.

Таблица 1.1 -- Сравнительный анализ методов рекомендательных систем

| Критерий | Контентная фильтрация | Коллаборативная фильтрация | Гибридный (EMZ View) |
|---|---|---|---|
| Холодный старт | Хорошо | Плохо | Хорошо |
| Разнообразие выдачи | Низкое | Высокое | Высокое (MMR) |
| Объяснимость | Высокая | Низкая | Высокая |
| Требования к данным | Метаданные объектов | История взаимодействий | Оба типа |
| Масштабируемость | Высокая | Средняя | Средняя |
| Неожиданные рекомендации | Редко | Часто | Часто |

**Обоснование выбора серверной платформы.**

Для реализации Backend-сервиса выбран Node.js 20 LTS с фреймворком Express 4 [16]. Обоснование:

- Express -- наиболее зрелый и широко распространенный фреймворк с богатой экосистемой middleware;
- Единая кодовая база на JavaScript/ESM упрощает сопровождение совместно с Telegram-ботом;
- Аналог -- FastAPI (Python) -- проигрывает в скорости работы с MongoDB-драйвером в данном контексте.

Для хранения данных выбрана MongoDB 6 [18]. Схема документов изначально гибка, что позволяет эволюционировать структуру профиля пользователя без миграций. Коллекция `movies` хранит метаданные, необходимые ML-сервису, непосредственно в BSON.

# 2 Проектирование системы

## 2.1 Архитектура системы EMZ View

Проектирование системы EMZ View основано на принципах микросервисной архитектуры. Монолитная альтернатива была отклонена по следующим причинам:
- ML-компонент требует Python-экосистему, несовместимую с Node.js-монолитом;
- ML-сервис требует значительно больше CPU/RAM при перестроении модели, чем Backend при обработке API-запросов -- раздельное масштабирование обязательно;
- Telegram-бот является автономным долгоживущим процессом с независимым жизненным циклом;
- Перезапуск Frontend (пересборка статики) не должен влиять на доступность API.

Backend реализует детерминированный кэш рекомендаций в памяти процесса. Ключ кэша включает подпись текущего состояния оценок пользователя:

```
cacheKey = `for-you:${userId}:${count}:${lastUpdatedISO}:${mediaType}:${limit}`
```

Подпись инвалидируется при каждом новом лайке или дизлайке без необходимости явного сброса кэша. TTL по умолчанию -- 120 секунд. При недоступности ML-сервиса Backend возвращает пустой список с полем `strategy: "unavailable"`, что обеспечивает работоспособность системы в деградированном режиме без ошибок 5xx.

Коллекция `movies` является ключевым хранилищем, обеспечивающим как отображение карточек пользователю, так и снабжение ML-сервиса текстовыми признаками. ## 2.5 Проектирование алгоритмического ядра

**Алгоритм построения TF-IDF-модели.**

Контентная модель строится из коллекции `movies` MongoDB. Для каждого объекта формируется текстовое представление с взвешиванием полей:

```
text(d) = title × 3 ⊕ genres × 2 ⊕ overview ⊕ cast ⊕ keywords
```

где символ ⊕ обозначает конкатенацию строк, а умножение -- повторение токенов (реализует частотное взвешивание в рамках TF-IDF без изменения алгоритма). (2.1)

TF-IDF-матрица T ∈ R^(n×v) формируется параметрами: max_features = 50 000 (словарь), ngram_range = (1, 2) (монограммы и биграммы), stop_words = "english". Этот подход соответствует рекомендациям [13].

На рисунке 2.7 представлена блок-схема алгоритма формирования персональных рекомендаций.

```
НАЧАЛО
  │
  ▼
Получить взаимодействия пользователя из MongoDB
  │
  ▼
|interactions| >= COLLAB_MIN (8)?
  │ Да                  │ Нет
  ▼                     ▼
Получить матрицу   Извлечь liked_ids
рейтингов          (value = 1)
  │                     │

```

Рисунок 2.7 -- Блок-схема алгоритма построения персональных рекомендаций

**Алгоритм MMR (Maximal Marginal Relevance).**

Алгоритм MMR итеративно отбирает объекты, максимизируя формулу (1.6). Псевдокод алгоритма:

```
Вход: candidates (отсортированные по score), λ, limit
Выход: selected (список объектов с улучшенным разнообразием)

selected ← []
remaining ← candidates

пока |remaining| > 0 и |selected| < limit:
    best_score ← -∞
    best_item ← None

    для каждого item в remaining:
        rel_score ← item.score
        если |selected| = 0:
            mmr ← λ × rel_score
        иначе:
            max_sim ← max(cos(TF-IDF[item], TF-IDF[s]) для s ∈ selected)
            mmr ← λ × rel_score - (1 - λ) × max_sim

        если mmr > best_score:
            best_score ← mmr
            best_item ← item

    selected.append(best_item)
    remaining.remove(best_item)

вернуть selected
```

**Параметры алгоритмов рекомендательной системы.**

| Параметр | Переменная окружения | Значение по умолчанию | Описание |
|---|---|---|---|
| k (SVD) | -- (hardcoded) | 32 | Размерность латентного пространства |
| Порог переключения | COLLAB_MIN_INTERACTIONS | 8 | Мин. взаимодействий для CF |

## 2.6 Проектирование пользовательских сценариев

**Сценарий онбординга.**

Онбординг решает проблему холодного старта за минимальное число шагов:
1. После регистрации пользователь перенаправляется на страницу `/onboarding`.
2. Frontend загружает кандидатов через API (параллельные запросы к TMDB: trending + popular + top_rated для фильмов и сериалов).
3. Пользователь выбирает не менее 12 понравившихся объектов из предлагаемой сетки.
4. Бесконечная прокрутка через `IntersectionObserver` подгружает следующие страницы кандидатов.
5. Нажатие «Продолжить» сохраняет выбор через `PUT /api/users/onboarding`, автоматически создавая записи `Rating` с `value = 1`.
6. Пользователь перенаправляется на главную страницу с уже персонализированной лентой.

**Сценарий взаимодействия через Telegram-бот.**

1. `/start` -- авторизация по Telegram ID через `BOT_SHARED_SECRET`. При первом подключении запрашивается email для связи аккаунта; после привязки отображается главное меню.
2. Кнопка «✨ Что посмотреть?» -- запрос `/api/recommendations/for-you`, 3 карточки с инлайн-клавиатурой.
3. Кнопка «🎭 По настроению» -- клавиатура с 7 настроениями; выбор запрашивает `/api/recommendations/mood`.
4. Кнопки «👍»/«👎» на карточке -- синхронизация оценки с веб-профилем через `/api/actions/rate`; клавиатура карточки обновляется без перерисовки сообщения.
5. Кнопка «📜 История» -- последние 5 оценок пользователя.
6. Кнопка «🔖 Хочу посмотреть» -- список закладок с ссылкой на сайт.
7. Кнопка «⚙️ Настройки» -- подменю: помощь, выход из аккаунта, ссылка на сайт.

Если сессия истекла и пользователь нажимает защищенную кнопку, бот показывает callback-уведомление («⚠️ Нужна авторизация») и сообщение с кнопкой «🚀 Авторизоваться» -- без необходимости вводить текстовую команду.

Ключевое проектное решение: бот не хранит пользовательских данных -- весь профиль находится в Backend, что обеспечивает единое пространство данных.

**Состояния пользовательского интерфейса.**

Для каждой витрины рекомендаций проектируются четыре состояния:
- **loading** -- skeleton-заглушки сохраняют макет;

Ниже приведен ключевой фрагмент middleware аутентификации (рисунок 3.2):

```javascript
// src/middleware/auth.js
export function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  const token = header?.startsWith('Bearer ')
    ? header.slice('Bearer '.length)
    : null;

  if (!token) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET);
    req.user = payload;
    return next();
  } catch {
    return res.status(401).json({ error: 'Unauthorized' });
  }
}
```

```python
import numpy as np

U, s, Vt = np.linalg.svd(mat, full_matrices=False)

kk = min(k, len(s))
user_factors = U[:, :kk] * s[:kk]   # (m, k)
item_factors = Vt[:kk, :].T          # (n, k)

# Предсказанные оценки для пользователя u:
scores = user_factors[user_idx] @ item_factors.T
```

**Реализация алгоритма MMR.**

Ключевой фрагмент реализации алгоритма MMR-перераспределения представлен на рисунке 3.8:

```python
# ml-service/app/services/hybrid.py (фрагмент)
def _mmr_rerank(candidates, lambda_mmr=0.7, limit=20):
    model = get_content_model()
    id_to_idx = {mid: i for i, mid in enumerate(model.ids)}
    selected_indices, remaining, result = [], list(candidates), []

    while remaining and len(result) < limit:
        best_score, best_pos = -float("inf"), 0
        for pos, item in enumerate(remaining):
            tmdb_id, rel_score = item[0], float(item[1])
            idx = id_to_idx.get(tmdb_id)
            if idx is None or not selected_indices:
                mmr = lambda_mmr * rel_score
            else:
                sims = cos_sim(model.tfidf[idx], model.tfidf[selected_indices])
                mmr = lambda_mmr * rel_score - (1-lambda_mmr) * float(np.max(sims))
            if mmr > best_score:
                best_score, best_pos = mmr, pos
        chosen = remaining.pop(best_pos)
        if id_to_idx.get(chosen[0]) is not None:
            selected_indices.append(id_to_idx[chosen[0]])
        result.append(chosen)
    return result
```

## 3.4 Реализация Telegram-бота

**Структура Telegram-бота.**

```
telegram-bot/
├── Dockerfile
├── package.json
└── src/
    └── index.js  # единственный модуль, Telegraf-бот
```

Бот реализован на Telegraf 4 с long polling. Состояние диалога хранится в `Map<chatId, SessionState>` в памяти процесса.

**Архитектура кнопочного интерфейса.**

Ключевым архитектурным решением является **полностью кнопочный UX**: единственная текстовая команда `/start` служит точкой входа, все остальное управление осуществляется через инлайн-клавиатуры. Это соответствует практике ведущих Telegram-продуктов: пользователь не должен запоминать команды.

При запуске (`/start`) бот регистрирует в Telegram-API только одну команду:

```javascript
await bot.telegram.setMyCommands([
  { command: 'start', description: 'Открыть главное меню' },
]);
```

Все остальные функции доступны только через кнопки, перечень которых приведен в таблице 3.3.

**HTML-форматирование карточек фильмов.**

За один запрос бот отправляет **3 карточки** (параметр `limit=3`), каждая — отдельным сообщением с собственной инлайн-клавиатурой. Это позволяет пользователю оценить любую из них независимо.

Карточки форматируются HTML-разметкой (режим `parse_mode: 'HTML'`), пример форматирования приведен на рисунке 3.16:

```javascript
// telegram-bot/src/index.js (фрагмент)
function formatCard(r, idx, total) {
  const typeLabel = r.mediaType === 'tv' ? '📺 Сериал' : '🎬 Фильм';
  const header = total > 1 ? `<b>[${idx + 1}/${total}]</b> ` : '';
  const overview = (r.overview ?? '').trim();
  const shortOverview = overview.length > 350
    ? overview.slice(0, 347) + '…' : overview;
  const explanation = (r.explanation ?? '').trim();

  let text = `${header}${typeLabel}  <b>${r.title}</b>`;
  if (shortOverview) text += `\n\n${shortOverview}`;
  if (explanation) text += `\n\n<i>💡 ${explanation}</i>`;
  return text;
}
```

Рисунок 3.16 -- Форматирование рекомендательной карточки в боте

После нажатия «👍» или «👎» клавиатура карточки обновляется (метод `editMessageReplyMarkup`): кнопки рейтинга заменяются на ✅/— или ❌/—, подтверждая сохраненную оценку без перерисовки сообщения.

**Онбординг и связка аккаунта в Telegram-боте.**

При первом запуске (`/start`) бот запрашивает email пользователя. Логика связки:

1. Backend проверяет, существует ли пользователь с таким `telegramUserId`;
2. Если нет — требует `email` → ищет аккаунт по email → привязывает TG-id или создает новый аккаунт;
3. После успешной привязки возвращает JWT; бот сохраняет его в `Map<chatId, SessionState>` и показывает главное меню с именем пользователя.

Если пользователь не авторизован и нажимает любую защищенную кнопку, бот показывает всплывающее уведомление (`answerCbQuery` с `show_alert: true`) и/или сообщение с кнопкой «🚀 Авторизоваться», которая повторяет поток авторизации без необходимости вводить текстовую команду. Полный листинг Telegram-бота приведен в Приложении В.

Выход из аккаунта реализован через кнопку «🚪 Выйти» в подменю ⚙️ Настройки: JWT в сессии обнуляется, пользователю показывается кнопка для повторного входа.

## 3.6 Выводы по третьей главе

Реализованы все четыре компонента системы EMZ View. Backend реализует 32 REST-эндпоинта (задокументированы в таблице 2.1) с JWT-аутентификацией, rate limiting, детерминированным кэшем и деградированным режимом при недоступности ML-сервиса. ML-сервис реализует 5 стратегий рекомендаций с улучшенным взвешенным TF-IDF, SVD-факторизацией и MMR-перераспределением. Frontend реализует 11-страничное SPA с поддержкой темной/светлой темы, watchlist, синхронизацией через CustomEvent, публичной лендинг-страницей, страницей настроек с восстановлением пароля, показом/скрытием пароля и индикатором надежности пароля. Telegram-бот реализован на полностью кнопочном UX: единственная текстовая команда `/start` служит точкой входа, все остальное управление осуществляется через инлайн-клавиатуры с 5 пунктами главного меню и подменю настроек.

Программная реализация создала полный работающий стек, готовый к верификации: в четвертой главе проводится его тестирование по разработанному набору тест-кейсов и оценка производительности ключевых эндпоинтов.

# 4 Тестирование системы

## 4.1 Стратегия и виды тестирования

Тестирование системы EMZ View проводилось на нескольких уровнях:
1. **Функциональное тестирование Backend API** -- проверка соответствия поведения эндпоинтов спецификации;
2. **Тестирование ML-сервиса** -- верификация стратегий рекомендаций и алгоритма MMR;
3. **Тестирование пользовательского интерфейса (UI-тестирование)** -- проверка ключевых пользовательских сценариев;
4. **Оценка производительности** -- измерение времени отклика ключевых эндпоинтов.

Тестирование проводилось в соответствии с процессами верификации и валидации, определенными в ГОСТ Р ИСО/МЭК 12207-2010 [1], методом «черного ящика» по заранее разработанным тест-кейсам (таблицы 4.1--4.8). Автоматизированные юнит-тесты не включены в объем данной работы и обозначены как направление дальнейшего развития.

# Заключение

В ходе выполнения выпускной квалификационной работы разработана и программно реализована гибридная рекомендательная система фильмов и сериалов EMZ View с мультиплатформенным интерфейсом. Система решает актуальную проблему персонализации контента в условиях информационного изобилия видеостримингового рынка.

Все четыре поставленные задачи решены в полном объеме:

**Задача 1** (Глава 1). Исследована предметная область рекомендательных систем: выявлены ключевые ограничения существующих подходов (проблема холодного старта, однообразие выдачи, отсутствие объяснимости) и обоснован выбор гибридной стратегии (TF-IDF + SVD + MMR). Проведен сравнительный анализ четырех аналогов (Netflix, Kinopoisk, IMDb, Letterboxd), выявлены незакрытые потребности: объяснимость рекомендаций, рекомендации по настроению, Telegram-канал, онбординг для холодного старта. Сформированы 15 функциональных требований (ФТ-01 -- ФТ-15) и 12 нефункциональных требований (НФТ-01 -- НФТ-12). Обоснован технологический стек: Node.js 20, Python 3.12, React 18, MongoDB 6, Telegraf 4.

**Задача 2** (Глава 2). Спроектирована микросервисная архитектура системы EMZ View: построены архитектурно-технологическая диаграмма (рис. 2.1), документная модель данных четырех коллекций MongoDB (рис. 2.2), API-спецификация 32 эндпоинтов Backend и 5 эндпоинтов ML-сервиса (таблицы 2.1, 2.2), UML-диаграммы вариантов использования, последовательностей и компонентов (рис. 2.3--2.6). Спроектировано алгоритмическое ядро: взвешенное TF-IDF-представление, SVD-факторизация (k = 32), user-user CF (30 соседей) и MMR (λ = 0,7).

**Задача 3** (Глава 3). Программно реализованы все четыре компонента системы: Backend-сервис (Node.js 20 + Express 4, 32 REST-эндпоинта, JWT, TTL-кэш, LLM-модуль, graceful degradation), ML-сервис (Python 3.12 + FastAPI, 5 стратегий рекомендаций, 7 настроений), Frontend-приложение (React 18, 11 страниц, темная/светлая тема, IntersectionObserver) и Telegram-бот (Telegraf 4, кнопочный UX, 7 настроений). Все компоненты упакованы в Docker Compose с единым `.env`.

**Задача 4** (Глава 4). Проведено функциональное тестирование по 62 тест-кейсам (аутентификация, действия, рекомендации, watchlist, ML-стратегии, UI, бот) -- все тест-кейсы прошли успешно. Верифицирован алгоритм MMR: разнообразие топ-10 улучшилось на 32%, число уникальных жанров выросло на 76%. Подтверждено выполнение нефункциональных требований: кэшированные рекомендации -- 23 мс (≤ 50 мс), первичный запрос -- 212 мс (≤ 500 мс).

**Основные количественные результаты работы:**
- 32 REST-эндпоинта Backend API + 5 эндпоинтов ML API;
- 4 коллекции MongoDB с обоснованной схемой и индексами;
- 5 стратегий рекомендаций с 7 поддерживаемыми настроениями;
- 11 страниц Frontend-приложения;
- 62 тест-кейса функционального тестирования;
- время отклика кэшированных рекомендаций -- 23 мс.

Практическим результатом работы является полнофункциональная система, готовая к развертыванию в одну команду (`docker compose up --build`) и пригодная для использования как основа коммерческого сервиса рекомендаций или референсная архитектура для обучения студентов направления «Прикладная информатика» в области рекомендательных систем и микросервисной разработки.

**Направления дальнейшего развития системы:**
1. **Автоматизированные тесты**: добавление unit-тестов (Jest, pytest) и интеграционных тестов (Supertest) для CI/CD-пайплайна с покрытием ≥ 80%.
2. **Implicit Feedback ALS**: использование библиотеки `implicit` для матричной факторизации с учетом неявных сигналов (время просмотра, прокрутка, число повторных посещений карточки).
3. **A/B-тестирование стратегий**: инфраструктура для сравнения качества стратегий рекомендаций на реальном трафике по метрике CTR и времени до первого клика.
4. **Персонализированные Push-уведомления**: ежедневная рассылка рекомендаций через Telegram-бот на основе актуального профиля пользователя.
5. **Горизонтальное масштабирование**: введение Redis как внешнего кэша рекомендаций для поддержки множества экземпляров Backend.

```javascript
// backend/src/middleware/auth.js (полный код)
import jwt from 'jsonwebtoken';

export function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  const token = header?.startsWith('Bearer ')
    ? header.slice('Bearer '.length)
    : null;

  if (!token) {
    return res.status(401).json({ error: 'Unauthorized' });
  }

  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    return next();
  } catch {
    return res.status(401).json({ error: 'Unauthorized' });
  }
}
```

**Формирование подписи рейтингов (cache invalidation).**

```javascript
// backend/src/routes/recommendations.js (фрагмент)
async function getRatingsSignature(userId) {
  const [count, last] = await Promise.all([
    Rating.countDocuments({ userId }),
    Rating.findOne({ userId })
      .sort({ updatedAt: -1, _id: -1 })
      .select({ updatedAt: 1 })
      .lean(),
  ]);
  const t = last?.updatedAt
    ? new Date(last.updatedAt).toISOString()
    : 'none';
  return `${count}:${t}`;
}
```

```python
class Interaction(BaseModel):

class UserProfile(BaseModel):
    user_id: str

class MoodRequest(BaseModel):
    mood: Literal["fun","sad","tense","chill","romantic","action","horror"]
    limit: int = 20

class Recommendation(BaseModel):
    tmdb_id: int
    media_type: Optional[Literal["movie", "tv"]] = None
    score: float
    explanation: Optional[str] = None

class RecommendResponse(BaseModel):
    strategy: str
```

```javascript
bot.start(async (ctx) => {
  const s = getSession(ctx.from.id);
  s.pendingEmail = false;

    const { data } = await backend.post('/api/auth/telegram', {
      telegramUserId: ctx.from.id,
      secret: process.env.BOT_SHARED_SECRET,
    });
    s.jwt = data.token;
    const firstName = ctx.from.first_name ?? 'друг';
    await ctx.replyWithHTML(
      `👋 Привет, <b>${firstName}</b>!\n\n${MAIN_MENU_TEXT}`,
      MAIN_MENU,
    );
  } catch (err) {
    const msg = err?.response?.data?.error;
    if (msg === 'email is required for first-time Telegram link') {
      s.pendingEmail = true;
      await ctx.replyWithHTML(
        '👋 <b>Первый запуск!</b>\n\nВведите email аккаунта EMZ View:',
        Markup.inlineKeyboard([[Markup.button.url('🌐 Сайт', FRONTEND_URL)]]),
      );
    }
  }
});
```

```javascript
// telegram-bot/src/index.js (фрагмент)
async function sendRecommendations(ctx, jwt, params = {}) {
  const mood = typeof params?.mood === 'string' ? params.mood : null;
  const count = params?.count ?? 3;
  const endpoint = mood
    ? '/api/recommendations/mood'
    : '/api/recommendations/for-you';
  const queryParams = mood
    ? { mood, limit: count }
    : { limit: count };

  const { data } = await backend.get(endpoint, {
    params: queryParams,
    headers: { Authorization: `Bearer ${jwt}` },
  });

  const recs = data.recommendations ?? [];
  for (const [i, r] of recs.entries()) {
    await ctx.replyWithHTML(
      formatCard(r, i, recs.length),
      cardKeyboard(r),
    );
  }
}

bot.action('menu:recommend', async (ctx) => {
  await ctx.answerCbQuery('🔍 Ищу для тебя…');
  const s = getSession(ctx.from.id);
  if (!s?.jwt) return ctx.replyWithHTML('🔐 Нужна авторизация.',
    Markup.inlineKeyboard([[
      Markup.button.callback('🚀 Авторизоваться', 'auth:restart'),
    ]]));
  await sendRecommendations(ctx, s.jwt);
});
```
