# Введение

Актуальность темы исследования. Цифровая трансформация индустрии развлечений привела к беспрецедентному росту объема доступного видеоконтента. По данным аналитического агентства Statista, к 2024 году совокупные библиотеки глобальных потоковых сервисов (Netflix, Amazon Prime Video, Disney+, Kinopoisk HD и др.) превысили 1,5 миллиона наименований фильмов и сериалов [23]. Российский рынок онлайн-кинотеатров демонстрирует устойчивый рост: по данным отраслевых аналитических агентств, совокупная аудитория легальных видеосервисов России достигла 90 миллионов уникальных пользователей в год, тогда как объем рынка ежегодно увеличивается на 20--25% [23].

В условиях подобного информационного изобилия стандартные механизмы поиска и фильтрации (по жанру, году выпуска, рейтингу) перестают эффективно решать задачу помощи пользователю. Исследования в области когнитивной психологии фиксируют феномен «паралича выбора» (англ. choice overload): при наличии избыточного числа альтернатив пользователь тратит на выбор несоразмерно много времени, испытывает неудовлетворенность и с высокой вероятностью покидает платформу без целевого действия. По оценкам компании Netflix, внедрение персонализированных рекомендаций позволило сократить показатель отказов (churn rate) на 25% и сэкономить более 1 млрд долларов в год благодаря удержанию подписчиков [13].

Актуальность темы усиливается тем, что современные пользователи взаимодействуют с контентом через множество каналов: десктопный браузер, мобильное приложение, телевизионные приставки, мессенджеры. Мультиплатформенность порождает новые инженерные вызовы: необходимо обеспечить единый профиль предпочтений и непрерывный пользовательский опыт независимо от канала доступа. Telegram как канал дистрибуции контентных рекомендаций приобрел особую значимость: аудитория мессенджера в России к 2025 году превысила 80 миллионов активных пользователей, при этом 68% из них ежедневно взаимодействуют с сервисными ботами и тематическими каналами [22], что позволяет охватывать целевую аудиторию видеосервисов без необходимости установки отдельного мобильного приложения.

Степень разработанности темы. Теоретическая база рекомендательных систем подробно освещена в фундаментальных работах Риччи, Рокача и Шапиры [13], а также в актуальном систематическом обзоре Роя и Дутты, охватывающем более 100 современных подходов к построению рекомендательных систем с учетом эволюции методов в 2018--2022 годах [14]. Сравнительный анализ методов матричной факторизации и нейросетевых подходов в задаче коллаборативной фильтрации выполнен в работе Рендла и соавторов [12], где показано, что корректно реализованная матричная факторизация остается конкурентоспособной с глубокими нейросетевыми моделями на современных бенчмарках и превосходит их по интерпретируемости и скорости обучения. Самообучающиеся методы и использование неявных сигналов взаимодействия как актуальное направление развития коллаборативной фильтрации систематизированы в обзоре Ю и соавторов [16].

Контентная фильтрация на основе TF-IDF и косинусного сходства рассмотрена в работах по информационному поиску [2], а современные сравнительные оценки качества факторизационных моделей на актуальных бенчмарках представлены в работе Zhang и соавторов [17]. Алгоритм MMR (Maximal Marginal Relevance), применяемый для улучшения разнообразия выдачи, был предложен Карбонеллом и Голдштейном [8] и впоследствии успешно адаптирован к задачам рекомендаций контента в ряде независимых исследований.

Вопросы объяснимости рекомендаций (explainable recommendations) активно исследуются в последние годы [6]; доказано, что понимание причин рекомендации повышает доверие пользователей и конверсию. Вместе с тем вопросы интеграции нескольких стратегий рекомендаций (гибридный подход) в единой мультиплатформенной системе с поддержкой объяснимости выдачи и рекомендаций по эмоциональному контексту остаются недостаточно проработанными в открытых прикладных реализациях. Большинство учебных проектов ограничиваются реализацией одного метода без инфраструктуры промышленного уровня.

Проблема исследования состоит в противоречии между потребностью рынка в персонализированных, объяснимых и мультиплатформенных рекомендациях и недостаточной проработанностью архитектурных и алгоритмических решений для систем среднего масштаба, не имеющих ресурсов Netflix или Яндекса. Конкретно, проблема заключается в необходимости создания системы, которая:
– обеспечивает персонализированные рекомендации с первого сеанса работы (решение проблемы холодного старта через онбординг);
– предоставляет объяснимые, разнообразные рекомендации по нескольким стратегиям (For You, Because, Mood, Similar Users);
– работает в нескольких пользовательских каналах (веб-приложение и Telegram-бот) с единым профилем пользователя;
– устойчиво функционирует при частичной недоступности компонентов системы (graceful degradation).

# 1 Аналитический раздел

## 1.1 Анализ предметной области персонализированных рекомендаций

Рекомендательные системы (РС) решают задачу автоматического ранжирования множества объектов по индивидуальной полезности для конкретного пользователя. В прикладной постановке для видеосервисов это означает построение упорядоченного списка фильмов и сериалов, который снижает когнитивную нагрузку при выборе и повышает вероятность позитивной пользовательской реакции.

Жизненный цикл пользовательского взаимодействия с РС принято делить на три фазы. В начальной фазе (холодный старт) данных о пользователе недостаточно для построения индивидуального профиля. В адаптивной фазе накопленная история оценок позволяет системе корректировать рекомендации. В стабилизированной фазе профиль пользователя обретает устойчивость, и качество рекомендаций достигает плато [4].

Для предметной области кино- и сериального контента характерен ряд специфических особенностей. Во-первых, гетерогенность контента: фильмы и сериалы имеют разные паттерны потребления -- сериалы просматриваются эпизодически в течение недель, тогда как фильм завершается за один сеанс. Во-вторых, значительное влияние эмоционального контекста: пользователь может последовательно искать триллер, романтическую комедию и семейный мультфильм, в зависимости от настроения и компании. В-третьих, критическая роль объяснимости: пользователи доверяют рекомендациям значительно больше, если понимают, почему тот или иной объект им предложен [6]. В-четвертых, высокая значимость визуального UX: постер фильма является ключевым элементом интерфейса, влияющим на первичное решение об интересе. В-пятых, многоканальность взаимодействия: пользователи ожидают непрерывного опыта между веб-клиентом и мобильными мессенджерами.

Специфика рекомендательных задач в области видеоконтента в сравнении с другими предметными областями (электронная коммерция, новостные агрегаторы) определяется несколькими ключевыми факторами. Длительность потребления контента существенно выше, чем у товаров: пользователь инвестирует от 90 минут до нескольких часов в просмотр, что делает ошибочную рекомендацию значительно более затратной с точки зрения пользовательского опыта. Культурная специфика и языковая принадлежность контента создают дополнительный контекстный фильтр, влияющий на предпочтения независимо от жанровых характеристик. Высокая степень сезонности (праздничные комедии, летние блокбастеры) обуславливает необходимость учета временного контекста при формировании рекомендаций. Перечисленные особенности предметной области определили архитектурные и алгоритмические решения, принятые при разработке системы EMZ View.

В 2024--2026 годах ландшафт рекомендательных систем существенно изменился под влиянием трех ключевых тенденций. Во-первых, активное внедрение больших языковых моделей (LLM) в качестве дополнительного компонента рекомендательных конвейеров: LLM используются для семантического понимания контента, генерации объяснений на естественном языке и диалогового взаимодействия [11]. Во-вторых, рост требований к объяснимости и честности (fairness) алгоритмов со стороны регуляторов и пользователей: системы, не предоставляющие обоснования рекомендаций, воспринимаются как «черные ящики» с низким доверием. В-третьих, консолидация мессенджерных платформ как канала доступа к сервисам: по данным на начало 2026 года аудитория Telegram превысила 900 миллионов активных пользователей в месяц, причем в России мессенджер является одним из наиболее используемых мобильных приложений, что делает Telegram-канал стратегически значимым для охвата российской аудитории без установки отдельного нативного приложения. Все три тенденции нашли отражение в архитектуре системы EMZ View.

## 1.2 Обзор методов построения рекомендательных систем

Контентная фильтрация.

Контентная фильтрация формирует рекомендации на основе признаков объектов: жанров, описаний, актерского состава, ключевых слов. Пользователь получает рекомендации, схожие с теми, что ему уже понравились. Математически задача сводится к поиску объектов с максимальным косинусным сходством с профильным вектором пользователя [7]. Основы ранжирования объектов по индивидуальной полезности подробно рассматриваются в работе Агеева [2].

Профильный вектор формируется как взвешенное среднее TF-IDF-векторов понравившихся объектов:

**p** = (1/|L|) * Σ(i ∈ L) **d_i**, (1.1)

где L -- множество объектов, получивших положительную оценку, **d_i** -- TF-IDF-вектор объекта i.

Оценка сходства между профилем и объектом-кандидатом вычисляется через косинусное расстояние:

sim(**p**, **d_j**) = (**p** · **d_j**) / (||**p**|| * ||**d_j**||) (1.2)

Преимущества контентной фильтрации: не требует большого числа пользователей, прозрачно объясняется через сходство с уже оцененными объектами, устойчива к разреженности пользовательских данных. Недостатки: риск «пузыря фильтрации» (система замыкается на похожем контенте), зависимость от полноты метаданных, слабое использование коллективного поведения.

Коллаборативная фильтрация.

Коллаборативная фильтрация опирается на схожесть поведения пользователей или объектов [14]. Матрично-факторизационный подход (SVD) разлагает матрицу взаимодействий R ∈ R^(m×n) как:

**R** ≈ **U** · **Σ** · **V^T**, (1.3)

где **U** ∈ R^(m×k) -- матрица скрытых факторов пользователей, **V** ∈ R^(n×k) -- матрица скрытых факторов объектов, **Σ** -- диагональная матрица сингулярных значений, k << min(m, n) -- размерность латентного пространства. Математическая основа метода подробно изложена в работе Воронцова [3].

Оценка предпочтения пользователя u к объекту i:

r̂_ui = **u_u** · **v_i^T**, (1.4)

где **u_u** -- вектор латентных факторов пользователя, вычисляемый как:

**u_u** = **U**[u, :] · **Σ**[:k]. (1.5)

Коллаборативные алгоритмы традиционно верифицируются на наборе данных MovieLens. Современный обзор методов построения рекомендательных систем на основе графовых нейронных сетей, включая применение к задаче CF, представлен в работе Gao и соавторов [9]. Применение самообучения и неявных сигналов взаимодействия (история просмотров, клики) как направление развития современных рекомендательных систем систематизировано в обзоре Ю и соавторов [16] и обозначено как направление дальнейшего развития EMZ View (Раздел «Заключение»). Граф-нейросетевые расширения матричной факторизации -- в частности, модель LightGCN, упрощающая граф-свертку на двудольном графе пользователь-объект до чистого линейного агрегирования соседей [10], -- демонстрируют высокую точность на ряде бенчмарков, однако требуют накопленной истории взаимодействий для построения информативного графа, что делает их менее подходящими для рекомендательных систем среднего масштаба на старте.

Выбор матричной факторизации над более сложными нейросетевыми моделями для системы среднего масштаба обоснован результатами Рендла и соавторов [12]: при корректной настройке гиперпараметров SVD-факторизация достигает сопоставимого с нейросетевыми подходами качества при существенно меньших требованиях к объему данных и вычислительным ресурсам, что критично для стартового каталога EMZ View.

Преимущества: находит неожиданные рекомендации, эффективна при накопленной истории. Недостатки: проблема холодного старта, чувствительность к разреженности матрицы.

Гибридный подход и принцип MMR.

Гибридные системы объединяют достоинства обоих подходов [13]. В данной работе применяется переключаемая стратегия: при объеме взаимодействий менее порогового значения используется контентная фильтрация, при достижении порога подключается коллаборативная.

Актуальным направлением развития рекомендательных систем в 2024--2025 годах является интеграция больших языковых моделей (LLM). Согласно обзору Lin и соавторов [11], LLM могут выступать как генераторы объяснений рекомендаций, как средства семантического обогащения контентных представлений и как инструменты диалогового взаимодействия пользователя с системой. В системе EMZ View LLM используется опционально для переформулировки шаблонных объяснений на естественном языке, что соответствует паттерну «LLM as explainer».

Для улучшения разнообразия выдачи применяется алгоритм Maximal Marginal Relevance (MMR), предложенный Carbonell и Goldstein [8]:

MMR(d_i) = λ · sim(**p**, **d_i**) -- (1 -- λ) · max(j ∈ S) sim(**d_j**, **d_i**), (1.6)

где S -- множество уже выбранных объектов, λ ∈ [0, 1] -- параметр баланса между релевантностью и новизной. При λ = 1 MMR эквивалентен ранжированию по релевантности; при λ = 0 -- максимизирует разнообразие. В данной работе используется λ = 0,7, обеспечивающее приоритет релевантности при умеренном разнообразии.

Принципиальное преимущество MMR над наивной фильтрацией топ-N заключается в том, что итеративный жадный отбор объектов работает с уже отобранным множеством S, а не только с запросом пользователя. Это свойство алгоритма, изначально разработанного для диверсификации результатов информационного поиска, в контексте видеорекомендаций решает практическую проблему «тематического монополизма»: без MMR пользователю, проявившему интерес к триллерам, рекомендуется однотипный набор из 10 триллеров вместо сбалансированной подборки.

## 1.4 Требования к разрабатываемой системе

Процедура формирования требований проводилась в два этапа. На первом этапе из анализа предметной области и аналогов выведены функциональные потребности пользователя, ранжированные по принципу MoSCoW (Must Have / Should Have / Could Have). На втором этапе каждая потребность сопоставлена с конкретным компонентом архитектуры, что исключает неопределенность ответственности на этапе реализации. Такой подход позволяет избежать типичной для учебных проектов проблемы «размытой ответственности», когда одна функция дублируется в нескольких сервисах или, напротив, остается нереализованной.

При ранжировании требований по MoSCoW класс «Must Have» получили все требования, непосредственно формирующие ценностное предложение системы: персонализированная выдача (ФТ-04), онбординг для холодного старта (ФТ-03), объяснимость рекомендаций (ФТ-13) и мультиплатформенный бот (ФТ-15). Требования класса «Should Have» охватывают функции, повышающие пользовательский опыт, но не критичные для базового использования: рекомендации по настроению (ФТ-07), история оценок (ФТ-10), поиск (ФТ-11). Такое разграничение определяет минимально жизнеспособный продукт (MVP) системы: требования ФТ-01, ФТ-03, ФТ-04, ФТ-08, ФТ-13, ФТ-15 образуют ядро MVP, достаточное для демонстрации ценности пользователю. Все требования реализованы в полном объеме, что делает EMZ View полнофункциональной системой, а не прототипом.

## 1.5 Выбор технологического стека

Выбор технологий обусловлен требованиями к системе, зрелостью экосистемы и скоростью разработки.

Обоснование выбора серверной платформы.

Для реализации Backend-сервиса выбран Node.js 20 LTS с фреймворком Express 4 [18]. Обоснование:
– Node.js обеспечивает высокую конкурентность асинхронных операций ввода-вывода при работе с MongoDB и TMDB API;
– Express -- наиболее зрелый и широко распространенный фреймворк с богатой экосистемой middleware;
– Единая кодовая база на JavaScript/ESM упрощает сопровождение совместно с Telegram-ботом;
– Аналог -- FastAPI (Python) -- проигрывает в скорости работы с MongoDB-драйвером в данном контексте.

Для хранения данных выбрана MongoDB 6 [20]. Схема документов изначально гибка, что позволяет эволюционировать структуру профиля пользователя без миграций. Коллекция `movies` хранит метаданные, необходимые ML-сервису, непосредственно в BSON.

Источником метаданных фильмов служит TMDB API v3 [24] -- один из наиболее полных и актуальных открытых каталогов кино- и сериального контента.

Необходимо отдельно обосновать отклоненную альтернативу в части хранилища данных. PostgreSQL в качестве СУБД рассматривался как альтернатива MongoDB. Преимущество PostgreSQL -- строгая типизация схемы и ACID-транзакции -- не является значимым для данной задачи: история оценок записывается атомарными upsert-операциями, а транзакционная обработка нескольких коллекций не требуется. В то же время хранение полиморфных метаданных фильмов (переменное число жанров, участников съемочной группы, ключевых слов) в реляционной схеме потребовало бы как минимум трех дополнительных таблиц и трехстороннего JOIN при каждом построении TF-IDF-вектора. MongoDB позволяет хранить полный документ фильма денормализованным образом и читать его единым запросом, что критично для производительности ML-сервиса при пакетной обработке.

Обоснование выбора платформы ML-сервиса.

Для ML-сервиса выбран Python 3.11 с FastAPI 0.110 [19]. Python является де-факто стандартом для задач машинного обучения: библиотеки scikit-learn, numpy, scipy обеспечивают производительные реализации TF-IDF и SVD [5]. # 2 Проектирование системы

## 2.1 Архитектура системы EMZ View

Проектирование системы EMZ View основано на принципах микросервисной архитектуры. Монолитная альтернатива была отклонена по следующим причинам:
– ML-компонент требует Python-экосистему, несовместимую с Node.js-монолитом;
– ML-сервис требует значительно больше CPU/RAM при перестроении модели, чем Backend при обработке API-запросов -- раздельное масштабирование обязательно;
– Telegram-бот является автономным долгоживущим процессом с независимым жизненным циклом;
– Перезапуск Frontend (пересборка статики) не должен влиять на доступность API.

Рисунок 2.1 -- Архитектурно-технологическая диаграмма системы EMZ View

Все компоненты объединены в изолированную Docker-сеть `emz-net`. Межсервисное взаимодействие осуществляется через HTTP REST. Конфигурация всех сервисов управляется единым файлом `.env`.

При проектировании архитектуры были рассмотрены и отклонены две альтернативы. Первая -- единый Backend с встроенным Python-интерпретатором (через child_process) -- отклонена из-за невозможности масштабирования ML-компонента независимо от API. Вторая -- gRPC-взаимодействие между Backend и ML-сервисом -- отклонена в пользу HTTP REST как более простой и широко поддерживаемой формы API-интеграции, не требующей генерации protobuf-схем. Выбранное архитектурное решение позволяет в будущем заменить Backend на любой другой технологический стек, сохранив ML-контракт без изменений.

Кэширование и деградация сервисов.

Backend реализует детерминированный кэш рекомендаций в памяти процесса. Ключ кэша включает подпись текущего состояния оценок пользователя:

```
cacheKey = `for-you:${userId}:${count}:${lastUpdatedISO}:${mediaType}:${limit}`
```

Подпись инвалидируется при каждом новом лайке или дизлайке без необходимости явного сброса кэша. TTL по умолчанию -- 120 секунд. При недоступности ML-сервиса Backend возвращает пустой список с полем `strategy: "unavailable"`, что обеспечивает работоспособность системы в деградированном режиме без ошибок 5xx.

Обоснование структуры модели данных.

Коллекция `movies` является ключевым хранилищем, обеспечивающим как отображение карточек пользователю, так и снабжение ML-сервиса текстовыми признаками. Поля `genres`, `cast`, `keywords` намеренно денормализованы (вложены в документ), что исключает необходимость JOIN-запросов при построении TF-IDF-представлений.

Коллекция `ratings` использует составной уникальный индекс `{userId, tmdbId, mediaType}`, что гарантирует идемпотентность операции выставления оценки: повторный лайк обновляет существующую запись, не создавая дублей.

Поле `source` в `ratings` позволяет аналитически разделять оценки, выставленные через веб-интерфейс, от оценок, выставленных через Telegram-бот, не нарушая единство профиля пользователя.

Коллекция `watchlists` хранит список объектов, которые пользователь хочет посмотреть, также с составным уникальным индексом.

Выбор документной модели MongoDB в сравнении с реляционной (PostgreSQL) обусловлен следующими соображениями. Схема профиля пользователя включает динамически расширяемый набор предпочтений (список онбординговых выборов переменной длины), не укладывающийся в фиксированную схему таблицы без нормализации в отдельную таблицу предпочтений. Метаданные фильмов из TMDB API имеют нерегулярную структуру: поле `cast` может содержать от 0 до 30+ записей, поле `keywords` -- от 0 до 50+. Документная модель хранит эти данные непосредственно в `movies`, обеспечивая атомарное чтение всех признаков за один запрос к базе данных.

## 2.5 Проектирование алгоритмического ядра

Алгоритм построения TF-IDF-модели.

Контентная модель строится из коллекции `movies` MongoDB. Для каждого объекта формируется текстовое представление с взвешиванием полей:

text(d) = title × 3 ⊕ genres × 2 ⊕ overview ⊕ cast ⊕ keywords, (2.1)

где символ ⊕ обозначает конкатенацию строк, а умножение -- повторение токенов (реализует частотное взвешивание в рамках TF-IDF без изменения алгоритма).

TF-IDF-матрица T ∈ R^(n×v) формируется параметрами: max_features = 50 000 (словарь), ngram_range = (1, 2) (монограммы и биграммы), stop_words = 'english'. Реализация выполнена с использованием библиотеки scikit-learn [27] и математической экосистемы SciPy (NumPy, scipy.linalg) [15], что обеспечивает воспроизводимость результатов и промышленный уровень численной стабильности операций матричного разложения.

На рисунке 2.7 представлена блок-схема алгоритма формирования персональных рекомендаций.


Рисунок 2.7 -- Блок-схема алгоритма построения персональных рекомендаций

Алгоритм MMR (Maximal Marginal Relevance).

Алгоритм MMR итеративно отбирает объекты, максимизируя формулу (1.6). Псевдокод алгоритма:

```
Вход: candidates (отсортированные по score), λ, limit
Выход: selected (список объектов с улучшенным разнообразием)

selected ← []
remaining ← candidates

пока |remaining| > 0 и |selected| < limit:
    best_score ← -∞
    best_item ← None

    для каждого item в remaining:
        rel_score ← item.score
        если |selected| = 0:
            mmr ← λ × rel_score
        иначе:
            max_sim ← max(cos(TF-IDF[item], TF-IDF[s]) для s ∈ selected)
            mmr ← λ × rel_score - (1 - λ) × max_sim

        если mmr > best_score:
            best_score ← mmr
            best_item ← item

    selected.append(best_item)
    remaining.remove(best_item)

вернуть selected
```

Параметры алгоритмов рекомендательной системы.

Проектирование алгоритмов предусматривает следующие управляемые параметры (таблица 2.3).

Таблица 2.3 -- Параметры алгоритмов ML-сервиса

| Параметр | Переменная окружения | Значение по умолчанию | Описание |
|---|---|---|---|
| k (SVD) | -- (hardcoded) | 32 | Размерность латентного пространства |
| Порог переключения | COLLAB_MIN_INTERACTIONS | 8 | Мин. взаимодействий для CF |
| λ (MMR) | MMR_LAMBDA | 0.7 | Баланс релевантность/разнообразие |
| max_features | -- | 50 000 | Размер TF-IDF словаря |
| ngram_range | -- | (1, 2) | Монограммы + биграммы |
| k_neighbors | -- (hardcoded) | 30 | Число соседей в user-user CF |
| title boost | -- | × 3 | Повтор токенов заголовка |
| genre boost | -- | × 2 | Повтор токенов жанра |

Обоснование числовых значений параметров. Выбор размерности латентного пространства k=32 основан на эмпирическом правиле для систем среднего масштаба: при каталоге от 1 000 до 10 000 объектов значения k в диапазоне 20--50 обеспечивают приемлемое качество SVD-аппроксимации без существенного роста вычислительных затрат. Более высокие значения (k=64, k=128) дают незначительный прирост качества при удвоении-учетверении времени разложения. Порог переключения COLLAB_MIN_INTERACTIONS=8 выбран как компромисс между необходимостью накопить достаточно данных для корректной работы user-user CF (минимальная разреженность строки матрицы) и нежеланием держать пользователя на контентной стратегии слишком долго. Значение λ=0,7 для MMR обеспечивает приоритет релевантности при одновременном снижении монотонности выдачи, что подтверждено тестированием в §4.3.

## 2.6 Проектирование пользовательских сценариев

Сценарий онбординга.

Онбординг решает проблему холодного старта за минимальное число шагов:
1. После регистрации пользователь перенаправляется на страницу `/onboarding`.
2. Frontend загружает кандидатов через API (параллельные запросы к TMDB: trending + popular + top_rated для фильмов и сериалов).
3. Пользователь выбирает не менее 12 понравившихся объектов из предлагаемой сетки.
4. Бесконечная прокрутка через `IntersectionObserver` подгружает следующие страницы кандидатов.
5. Нажатие «Продолжить» сохраняет выбор через `PUT /api/users/onboarding`, автоматически создавая записи `Rating` с `value = 1`.
6. Пользователь перенаправляется на главную страницу с уже персонализированной лентой.

В ходе проектирования разработана микросервисная архитектура EMZ View с четырьмя независимыми компонентами. Построены: архитектурно-технологическая диаграмма (рис. 2.1), документная модель данных четырех коллекций MongoDB (рис. 2.2), API-спецификация более 30 ключевых эндпоинтов Backend и 5 эндпоинтов ML-сервиса, UML-диаграммы вариантов использования, последовательностей и компонентов (рис. 2.3--2.6), блок-схема алгоритма построения персональных рекомендаций (рис. 2.7).

Спроектировано алгоритмическое ядро ML-компонента: взвешенное TF-IDF-представление с полевым бустингом, SVD-матричная факторизация (k=32), user-user CF с 30 соседями и MMR-перераспределение с λ=0,7. Все алгоритмические параметры управляются через переменные окружения.

Ключевым проектным решением, определяющим качество пользовательского опыта, является разделение ответственности между Backend и ML-сервисом по принципу командной шины: Backend несет ответственность за персистентность, аутентификацию и кэширование, тогда как ML-сервис -- исключительно за вычислительную логику рекомендаций. Это разграничение позволяет перезапускать ML-сервис для пересборки модели без прерывания пользовательских сессий, что было бы невозможно при монолитной архитектуре. Второй ключевой проектной находкой является детерминированный кэш-ключ, основанный на подписи взаимодействий пользователя: это обеспечивает автоматическую инвалидацию кэша ровно в тот момент, когда поведение пользователя изменилось, -- без явного управления TTL.

Результаты проектирования служат исходной спецификацией для программной реализации, описываемой в третьей главе.

4. `express.json` -- парсинг JSON-тела запроса;
5. `requireAuth` -- JWT-проверка (монтируется на уровне роутера, не глобально).

Структурное логирование реализовано через библиотеку `winston` (модуль `src/lib/logger.js`): в режиме разработки используется цветной `simple`-формат в консоли, в production -- JSON-формат с временными метками. Полный листинг ключевых модулей Backend приведен в Приложении А.

Аутентификация и безопасность.

JWT-токен формируется с полезной нагрузкой `{userId, email, name}` и сроком действия `JWT_EXPIRES_IN` (по умолчанию 7 дней). Пароли хэшируются bcrypt с cost factor = 10.

Ниже приведен ключевой фрагмент middleware аутентификации (рисунок 3.2):

```javascript
// src/middleware/auth.js
export function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  const token = header?.startsWith('Bearer ')
    ? header.slice('Bearer '.length)
    : null;

  if (!token) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET);
    req.user = payload;
    return next();
  } catch {
    return res.status(401).json({ error: 'Unauthorized' });
  }
}
```

```python
# ml-service/app/services/collab.py (фрагмент)
import numpy as np

U, s, Vt = np.linalg.svd(mat, full_matrices=False)

kk = min(k, len(s))
user_factors = U[:, :kk] * s[:kk]   # (m, k)
item_factors = Vt[:kk, :].T          # (n, k)

# Предсказанные оценки для пользователя u:
scores = user_factors[user_idx] @ item_factors.T
```

Реализация алгоритма MMR.

Ключевой фрагмент реализации алгоритма MMR-перераспределения представлен на рисунке 3.8:

```python
# ml-service/app/services/hybrid.py (фрагмент)
def _mmr_rerank(candidates, lambda_mmr=0.7, limit=20):
    model = get_content_model()
    id_to_idx = {mid: i for i, mid in enumerate(model.ids)}
    selected_indices, remaining, result = [], list(candidates), []

    while remaining and len(result) < limit:
        best_score, best_pos = -float("inf"), 0
        for pos, item in enumerate(remaining):
            tmdb_id, rel_score = item[0], float(item[1])
            idx = id_to_idx.get(tmdb_id)
            if idx is None or not selected_indices:
                mmr = lambda_mmr * rel_score
            else:
                sims = cos_sim(model.tfidf[idx], model.tfidf[selected_indices])
                mmr = lambda_mmr * rel_score - (1-lambda_mmr) * float(np.max(sims))
            if mmr > best_score:
                best_score, best_pos = mmr, pos
        chosen = remaining.pop(best_pos)
        if id_to_idx.get(chosen[0]) is not None:
            selected_indices.append(id_to_idx[chosen[0]])
        result.append(chosen)
    return result
```

Рисунок 3.11 -- Реализация бесконечной прокрутки через IntersectionObserver

Сетка кандидатов загружается параллельно из шести источников TMDB (trending/popular/top_rated × movie/tv), что обеспечивает разнообразие контента уже на первом экране.

Техническое решение параллельной загрузки из шести источников имеет принципиальное значение для алгоритма онбординга. Если бы кандидаты брались из одного источника (например, только `trending`), пользователь, ориентирующийся на нишевые жанры (арт-хаус, аниме, документальное кино), не нашел бы достаточного числа подходящих объектов в первой порции и, с высокой вероятностью, прервал бы онбординг. Диверсификация источников обеспечивает статистически более равномерное покрытие жанрового пространства при любом размере первоначальной выборки. Дополнительно, `IntersectionObserver` с `rootMargin: '200px'` инициирует предзагрузку следующей страницы кандидатов до того, как пользователь достигнет нижней границы экрана, исключая воспринимаемые паузы прокрутки.

Этап 2. Онбординг. На странице `/onboarding` отображается сетка постеров из более чем 120 фильмов и сериалов (тренды, популярное и топ-рейтинговые из TMDB). После нажатия кнопки «Продолжить» система сохраняет выбор как положительные оценки и формирует начальный профиль предпочтений.

Этап 3. Главная страница (витрины рекомендаций). После онбординга открывается главная страница `/recommendations` с шестью горизонтальными витринами:

– «Похожий вкус» -- объекты, которые нравятся пользователям с похожими предпочтениями;
– «Потому что вам понравилось X» -- контентно-похожие объекты;
– три витрины «По настроению» (случайно выбранные из 7 доступных).

Каждая карточка содержит кнопки «👍» (лайк), «👎» (дизлайк) и «🔖» (добавить в список просмотра). Нажатие на постер открывает страницу с детальной информацией об объекте.

Для восстановления пароля используется механизм одноразового токена: пользователь запрашивает сброс на странице `/login` (ссылка «Забыли пароль?»), получает токен (в текущей реализации возвращается в ответе API при `NODE_ENV !== production`) и вводит его вместе с новым паролем на странице настроек.

## 3.4 Реализация Telegram-бота

Выбор Telegram как второго клиентского канала продиктован двумя факторами. С точки зрения охвата аудитории: Telegram является одним из наиболее используемых мессенджеров в России, его Bot API предоставляет богатый UI-примитив (инлайн-клавиатуры, HTML-форматирование) без необходимости разработки нативного мобильного приложения [22]. С инженерной точки зрения: бот работает с теми же REST-эндпоинтами Backend, что и веб-клиент, -- единый профиль пользователя и оценки синхронизируются между платформами в реальном времени, что подтверждает корректность API-first-дизайна системы.

Структура Telegram-бота.

```
telegram-bot/
├── Dockerfile
├── package.json
└── src/
    └── index.js  # единственный модуль, Telegraf-бот
```

Бот реализован на Telegraf 4 с long polling. Состояние диалога хранится в `Map<chatId, SessionState>` в памяти процесса.

Ключевым архитектурным решением является полностью кнопочный UX: единственная текстовая команда `/start` служит точкой входа, все остальное управление осуществляется через инлайн-клавиатуры. Это соответствует практике ведущих Telegram-продуктов: пользователь не должен запоминать команды.

При запуске (`/start`) бот регистрирует в Telegram-API только одну команду:

```javascript
await bot.telegram.setMyCommands([
  { command: 'start', description: 'Открыть главное меню' },
]);
```

HTML-форматирование карточек фильмов.

За один запрос бот отправляет 3 карточки (параметр `limit=3`), каждая — отдельным сообщением с собственной инлайн-клавиатурой. Это позволяет пользователю оценить любую из них независимо.

Карточки форматируются HTML-разметкой (режим `parse_mode: 'HTML'`), пример форматирования приведен на рисунке 3.16:

```javascript
// telegram-bot/src/index.js (фрагмент)
function formatCard(r, idx, total) {
  const typeLabel = r.mediaType === 'tv' ? '📺 Сериал' : '🎬 Фильм';
  const header = total > 1 ? `<b>[${idx + 1}/${total}]</b> ` : '';
  const overview = (r.overview ?? '').trim();
  const shortOverview = overview.length > 350
    ? overview.slice(0, 347) + '…' : overview;
  const explanation = (r.explanation ?? '').trim();

  let text = `${header}${typeLabel}  <b>${r.title}</b>`;
  if (shortOverview) text += `\n\n${shortOverview}`;
  if (explanation) text += `\n\n<i>💡 ${explanation}</i>`;
  return text;
}
```

Рисунок 3.16 -- Форматирование рекомендательной карточки в боте

После нажатия «👍» или «👎» клавиатура карточки обновляется (метод `editMessageReplyMarkup`): кнопки рейтинга заменяются на ✅/— или ❌/—, подтверждая сохраненную оценку без перерисовки сообщения.

Онбординг и связка аккаунта в Telegram-боте.

При первом запуске (`/start`) бот запрашивает email пользователя. Логика связки:

1. Backend проверяет, существует ли пользователь с таким `telegramUserId`;
2. Если нет — требует `email` → ищет аккаунт по email → привязывает TG-id или создает новый аккаунт;
3. После успешной привязки возвращает JWT; бот сохраняет его в `Map<chatId, SessionState>` и показывает главное меню с именем пользователя.

Если пользователь не авторизован и нажимает любую защищенную кнопку, бот показывает всплывающее уведомление (`answerCbQuery` с `show_alert: true`) и/или сообщение с кнопкой «🚀 Авторизоваться», которая повторяет поток авторизации без необходимости вводить текстовую команду. Полный листинг Telegram-бота приведен в Приложении В.

Выход из аккаунта реализован через кнопку «🚪 Выйти» в подменю ⚙️ Настройки: JWT в сессии обнуляется, пользователю показывается кнопка для повторного входа.

## 3.6 Выводы по третьей главе

Реализованы все четыре компонента системы EMZ View. Backend реализует 33 REST-эндпоинта (задокументированы в таблице 2.1) с JWT-аутентификацией, rate limiting, детерминированным кэшем и деградированным режимом при недоступности ML-сервиса. ML-сервис реализует 5 стратегий рекомендаций с улучшенным взвешенным TF-IDF, SVD-факторизацией и MMR-перераспределением. Frontend реализует 11-страничное SPA с поддержкой темной/светлой темы, watchlist, синхронизацией через CustomEvent, публичной лендинг-страницей, страницей настроек с восстановлением пароля, показом/скрытием пароля и индикатором надежности пароля. Telegram-бот реализован на полностью кнопочном UX: единственная текстовая команда `/start` служит точкой входа, все остальное управление осуществляется через инлайн-клавиатуры с 5 пунктами главного меню и подменю настроек.

В процессе реализации выявлен ряд нетривиальных инженерных задач, потребовавших специфических решений. Синхронизация состояния лайков между несколькими экземплярами компонента «карточка фильма» на одной странице решена через Custom DOM Events (`emz:rating`), что позволило избежать избыточного перерендеринга при использовании глобального стейт-менеджера. Деградированный режим Backend при недоступности ML-сервиса реализован через паттерн «обертки с fallback»: функция `safeGetRecommendations` перехватывает сетевые ошибки на уровне HTTP-клиента и возвращает пустой список вместо статуса 500, что соответствует требованию НФТ-03. Бот не хранит пользовательских данных в локальном хранилище -- весь профиль находится в Backend, что обеспечивает единое пространство данных и гарантирует согласованность оценок между веб-клиентом и Telegram-каналом.

Программная реализация создала полный работающий стек, готовый к верификации: в четвертой главе проводится его тестирование по разработанному набору тест-кейсов и оценка производительности ключевых эндпоинтов.

# 4 Тестирование системы

## 4.1 Стратегия и виды тестирования

Тестирование системы EMZ View проводилось на нескольких уровнях:
1. Функциональное тестирование Backend API -- проверка соответствия поведения эндпоинтов спецификации;
2. Тестирование ML-сервиса -- верификация стратегий рекомендаций и алгоритма MMR;
3. Тестирование пользовательского интерфейса (UI-тестирование) -- проверка ключевых пользовательских сценариев;
4. Оценка производительности -- измерение времени отклика ключевых эндпоинтов.

Тестирование проводилось в соответствии с процессами верификации и валидации, определенными в ГОСТ Р ИСО/МЭК 12207-2010 [1], методом «черного ящика» по заранее разработанным тест-кейсам (таблицы 4.1--4.8). Автоматизированные юнит-тесты не включены в объем данной работы и обозначены как направление дальнейшего развития.

Классификация тест-кейсов выполнена по принципу функциональной декомпозиции: каждая логическая группа тест-кейсов соответствует одному сервису или функциональному модулю системы. Такой подход позволяет независимо оценивать качество каждого компонента и точно локализовать дефекты без необходимости запускать весь стек. Для тестирования API-эндпоинтов использовался инструмент Hoppscotch (веб-альтернатива Postman), что обеспечило воспроизводимость тестовых сценариев путем экспорта коллекций в JSON-формат.

Выбор метода «черного ящика» обусловлен несколькими факторами. При тестировании REST API наблюдателю доступны только входные параметры запроса и выходной HTTP-ответ, что полностью соответствует семантике метода. Кроме того, тестирование по контракту (API contract testing) позволяет независимо верифицировать каждый сервис: тест-кейсы для Backend API не зависят от деталей реализации алгоритмов ML-сервиса, что упрощает локализацию дефектов. Тест-кейсы разработаны до начала реализации соответствующих эндпоинтов, что обеспечивает независимость тестирования от конкретной реализации.

Вторая зона -- ML-зависимые операции с промахом кэша: 165--212 мс, где доминирует время сериализации данных, их передачи по Docker-сети и вычислений в ML-сервисе (TF-IDF умножение профильного вектора на матрицу T или SVD-скоринг). Третья зона -- операции с попаданием в кэш: 23 мс, что соответствует задержке чтения одного значения из Map и формирования JSON-ответа.

Практически значимым выводом является то, что разница между HIT и MISS для рекомендаций составляет 8--9 раз (23 мс vs 187--212 мс). Это подтверждает стратегическую правильность применения кэша: в типичном сценарии использования главная страница открывается многократно при просмотре, тогда как новые оценки, инвалидирующие кэш, выставляются значительно реже. Таким образом, средневзвешенное время отклика для реального пользователя оказывается значительно ниже теоретического максимума 212 мс.

Узкое место при масштабировании.

Потенциальным узким местом при значительном росте числа пользователей является хранение кэша рекомендаций в памяти одного процесса Backend. При горизонтальном масштабировании (несколько экземпляров Backend) каждый экземпляр будет иметь собственный кэш, что приведет к многократному дублированию ML-запросов. Проектным решением данной проблемы, вынесенным в направления дальнейшего развития, является введение Redis как внешнего хранилища кэша: все экземпляры Backend будут разделять единую кэш-запись, сохраняя преимущество 23 мс при HIT при любом уровне горизонтального масштабирования.

# Заключение

В ходе выполнения выпускной квалификационной работы разработана и программно реализована гибридная рекомендательная система фильмов и сериалов EMZ View с мультиплатформенным интерфейсом. Система решает актуальную проблему персонализации контента в условиях информационного изобилия видеостримингового рынка.

Научная новизна работы определяется комплексом оригинальных решений, не встречающихся в совокупности в открытых учебных реализациях: применение взвешенного TF-IDF с полевым бустингом заголовка и жанра для повышения точности контентного профиля; переключаемая стратегия (content-based при менее 8 взаимодействиях, коллаборативная при их накоплении); интеграция алгоритма MMR для одновременного контроля релевантности и разнообразия выдачи; рекомендации по эмоциональному настроению с семью поддерживаемыми семантическими контекстами; единый профиль пользователя для веб- и Telegram-каналов при полностью кнопочном UX-интерфейсе бота.

Следует особо выделить инженерную новизну реализованного решения для управления кэшем рекомендаций. В отличие от распространенного подхода TTL-based invalidation, в системе EMZ View применен принцип детерминированной сигнатурной инвалидации: ключ кэша формируется как хеш от числа оценок пользователя и временной метки последней оценки. Это позволяет автоматически инвалидировать кэш ровно в момент изменения поведения пользователя -- без периодических джобов и без риска устаревших рекомендаций. Данный подход обеспечивает одновременно высокую производительность (повторный запрос занимает 23 мс) и актуальность данных, что подтверждено в ходе тестирования (§4.4).

```javascript
import jwt from 'jsonwebtoken';

export function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  const token = header?.startsWith('Bearer ')
    ? header.slice('Bearer '.length)
    : null;

  if (!token) {
    return res.status(401).json({ error: 'Unauthorized' });
  }

  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    return next();
  } catch {
    return res.status(401).json({ error: 'Unauthorized' });
  }
}
```

```javascript
async function getRatingsSignature(userId) {
  const [count, last] = await Promise.all([
    Rating.countDocuments({ userId }),
    Rating.findOne({ userId })
      .sort({ updatedAt: -1, _id: -1 })
      .select({ updatedAt: 1 })
      .lean(),
  ]);
  const t = last?.updatedAt

    : 'none';
  return `${count}:${t}`;
}
```

```javascript
async function sendRecommendations(ctx, jwt, params = {}) {
  const mood = typeof params?.mood === 'string' ? params.mood : null;
  const count = params?.count ?? 3;
  const endpoint = mood
    ? '/api/recommendations/mood'
    : '/api/recommendations/for-you';
  const queryParams = mood
    ? { mood, limit: count }
    : { limit: count };

  const { data } = await backend.get(endpoint, {
    params: queryParams,

  for (const [i, r] of recs.entries()) {
    await ctx.replyWithHTML(
      formatCard(r, i, recs.length),
      cardKeyboard(r),
    );
  }
}
```
