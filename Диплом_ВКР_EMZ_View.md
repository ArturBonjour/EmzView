# Введение

Актуальность темы обусловлена стремительным ростом объема цифрового видеоконтента: по данным аналитического агентства Statista, к 2024 году мировые библиотеки потоковых сервисов превысили 1,5 миллиона наименований фильмов и сериалов [1]. В условиях подобного информационного изобилия стандартные механизмы поиска и фильтрации перестают справляться с задачей помощи пользователю: он сталкивается с феноменом «паралича выбора», что снижает удовлетворенность от использования платформы и увеличивает показатель отказов.

Рекомендательные системы сегодня являются одним из ключевых конкурентных преимуществ цифровых медиасервисов. По оценкам компании Netflix, более 80% просматриваемого контента выбирается пользователями именно через механизм рекомендаций [2]. Тем не менее разрыв между возможностями промышленных рекомендательных систем и типовыми реализациями в учебных и прикладных проектах остается значительным: последние нередко страдают от проблемы «холодного старта», слабой объяснимости выдачи, отсутствия мультиплатформенного взаимодействия и хрупкости при частичных отказах внешних сервисов.

Проблема исследования заключается в необходимости создания системы, которая:
- обеспечивает персонализированные рекомендации с первого сеанса работы (решение проблемы холодного старта);

- работает в нескольких пользовательских каналах (веб-приложение и Telegram-бот) с единым профилем пользователя;
- устойчиво функционирует при частичной недоступности компонентов системы.

Объект исследования -- процессы и методы персонализации контента в информационных системах рекомендаций фильмов и сериалов.

Предмет исследования -- методы, алгоритмы и программные средства построения гибридной рекомендательной системы с поддержкой объяснимости, разнообразия выдачи и мультиплатформенного взаимодействия.

# 1 Аналитический раздел

## 1.1 Анализ предметной области персонализированных рекомендаций

Рекомендательные системы (РС) решают задачу автоматического ранжирования множества объектов по индивидуальной полезности для конкретного пользователя. В прикладной постановке для видеосервисов это означает построение упорядоченного списка фильмов и сериалов, который снижает когнитивную нагрузку при выборе и повышает вероятность позитивной пользовательской реакции.

Жизненный цикл пользовательского взаимодействия с РС принято делить на три фазы. В начальной фазе (холодный старт) данных о пользователе недостаточно для построения индивидуального профиля. В адаптивной фазе накопленная история оценок позволяет системе корректировать рекомендации. В стабилизированной фазе профиль пользователя обретает устойчивость, и качество рекомендаций достигает плато [3].

Для предметной области кино- и сериального контента характерен ряд специфических особенностей. Во-первых, гетерогенность контента: фильмы и сериалы имеют разные паттерны потребления -- сериалы просматриваются эпизодически в течение недель, тогда как фильм завершается за один сеанс. Во-вторых, значительное влияние эмоционального контекста: пользователь может последовательно искать триллер, романтическую комедию и семейный мультфильм, в зависимости от настроения и компании. В-третьих, критическая роль объяснимости: пользователи доверяют рекомендациям значительно больше, если понимают, почему тот или иной объект им предложен [4]. В-четвертых, высокая значимость визуального UX: постер фильма является ключевым элементом интерфейса, влияющим на первичное решение об интересе. В-пятых, многоканальность взаимодействия: пользователи ожидают непрерывного опыта между веб-клиентом и мобильными мессенджерами.

## 1.2 Обзор методов построения рекомендательных систем

### 1.2.1 Контентная фильтрация

Контентная фильтрация формирует рекомендации на основе признаков объектов: жанров, описаний, актерского состава, ключевых слов. Пользователь получает рекомендации, схожие с теми, что ему уже понравились. Математически задача сводится к поиску объектов с максимальным косинусным сходством с профильным вектором пользователя [5].

Профильный вектор формируется как взвешенное среднее TF-IDF-векторов понравившихся объектов:

**p** = (1/|L|) * Σ(i ∈ L) **d_i**,

где L -- множество объектов, получивших положительную оценку, **d_i** -- TF-IDF-вектор объекта i. (1.1)

Оценка сходства между профилем и объектом-кандидатом вычисляется через косинусное расстояние:

sim(**p**, **d_j**) = (**p** · **d_j**) / (||**p**|| * ||**d_j**||) (1.2)

Преимущества контентной фильтрации: не требует большого числа пользователей, прозрачно объясняется через сходство с уже оцененными объектами, устойчива к разреженности пользовательских данных. Недостатки: риск «пузыря фильтрации» (система замыкается на похожем контенте), зависимость от полноты метаданных, слабое использование коллективного поведения.

### 1.2.2 Коллаборативная фильтрация

Коллаборативная фильтрация опирается на схожесть поведения пользователей или объектов [6]. Матрично-факторизационный подход (SVD) разлагает матрицу взаимодействий R ∈ R^(m×n) как:

**R** ≈ **U** · **Σ** · **V^T**, (1.3)

где **U** ∈ R^(m×k) -- матрица скрытых факторов пользователей, **V** ∈ R^(n×k) -- матрица скрытых факторов объектов, **Σ** -- диагональная матрица сингулярных значений, k << min(m, n) -- размерность латентного пространства.

Оценка предпочтения пользователя u к объекту i:

r̂_ui = **u_u** · **v_i^T**, (1.4)

где **u_u** = **U**[u, :] · **Σ**[:k] -- вектор латентных факторов пользователя. (1.5)

User-user коллаборативная фильтрация вычисляет сходство между целевым пользователем и соседями через косинусную меру, а затем агрегирует оценки взвешенной суммой [7].

Преимущества: находит неожиданные рекомендации, эффективна при накопленной истории. Недостатки: проблема холодного старта, чувствительность к разреженности матрицы.

### 1.2.3 Гибридный подход и принцип MMR

Гибридные системы объединяют достоинства обоих подходов [8]. В данной работе применяется переключаемая стратегия: при объеме взаимодействий менее порогового значения используется контентная фильтрация, при достижении порога подключается коллаборативная.

Для улучшения разнообразия выдачи применяется алгоритм Maximal Marginal Relevance (MMR), предложенный Carbonell и Goldstein [9]:

MMR(d_i) = λ · sim(**p**, **d_i**) -- (1 -- λ) · max(j ∈ S) sim(**d_j**, **d_i**), (1.6)

где S -- множество уже выбранных объектов, λ ∈ [0, 1] -- параметр баланса между релевантностью и новизной. При λ = 1 MMR эквивалентен ранжированию по релевантности; при λ = 0 -- максимизирует разнообразие. В данной работе используется λ = 0,7, обеспечивающее приоритет релевантности при умеренном разнообразии.

Таблица 1.1 -- Сравнительный анализ методов рекомендательных систем

| Критерий | Контентная фильтрация | Коллаборативная фильтрация | Гибридный (EMZ View) |
|---|---|---|---|
| Холодный старт | Хорошо | Плохо | Хорошо |

### 1.5.1 Обоснование выбора платформы Backend

Для реализации Backend-сервиса выбран Node.js 20 LTS с фреймворком Express 4. Обоснование:
- Node.js обеспечивает высокую конкурентность асинхронных операций ввода-вывода при работе с MongoDB и TMDB API;
- Express -- наиболее зрелый и широко распространенный фреймворк с богатой экосистемой middleware;
- Единая кодовая база на JavaScript/ESM упрощает сопровождение совместно с Telegram-ботом;
- Аналог -- FastAPI (Python) -- проигрывает в скорости работы с MongoDB-драйвером в данном контексте.

Для хранения данных выбрана MongoDB 6. Схема документов изначально гибка, что позволяет эволюционировать структуру профиля пользователя без миграций. Коллекция `movies` хранит метаданные, необходимые ML-сервису, непосредственно в BSON.

Для ML-сервиса выбран Python 3.12 с FastAPI 0.110. FastAPI превосходит Flask по скорости (асинхронный Starlette), автоматической валидации через Pydantic и встроенной документации OpenAPI.

### 1.5.3 Обоснование выбора Frontend-фреймворка

Для фронтенда выбран React 18 с Vite 5 в качестве сборщика. React -- доминирующий SPA-фреймворк с крупнейшей экосистемой компонентов. Vite обеспечивает HMR без перезапуска сборки и оптимизированный production-бандл через Rollup.

# 2 Проектирование системы

## 2.1 Архитектура системы EMZ View

### 2.1.1 Обоснование микросервисной архитектуры

Проектирование системы EMZ View основано на принципах микросервисной архитектуры. Монолитная альтернатива была отклонена по следующим причинам:
- ML-компонент требует Python-экосистему, несовместимую с Node.js-монолитом;
- ML-сервис требует значительно больше CPU/RAM при перестроении модели, чем Backend при обработке API-запросов -- раздельное масштабирование обязательно;
- Telegram-бот является автономным долгоживущим процессом с независимым жизненным циклом;
- Перезапуск Frontend (пересборка статики) не должен влиять на доступность API.

### 2.1.3 Принцип работы кэширования и деградации

Backend реализует детерминированный кэш рекомендаций в памяти процесса. Ключ кэша включает подпись текущего состояния оценок пользователя:

```
cacheKey = `for-you:${userId}:${count}:${lastUpdatedISO}:${mediaType}:${limit}`
```

Подпись инвалидируется при каждом новом лайке или дизлайке без необходимости явного сброса кэша. TTL по умолчанию -- 120 секунд. При недоступности ML-сервиса Backend возвращает пустой список с полем `strategy: "unavailable"`, что обеспечивает работоспособность системы в деградированном режиме без ошибок 5xx.

### 2.2.2 Обоснование структуры модели данных

Коллекция `movies` является ключевым хранилищем, обеспечивающим как отображение карточек пользователю, так и снабжение ML-сервиса текстовыми признаками. Коллекция `ratings` использует составной уникальный индекс `{userId, tmdbId, mediaType}`, что гарантирует идемпотентность операции выставления оценки: повторный лайк обновляет существующую запись, не создавая дублей.

Поле `source` в `ratings` позволяет аналитически разделять оценки, выставленные через веб-интерфейс, от оценок, выставленных через Telegram-бот, не нарушая единство профиля пользователя.

Коллекция `watchlists` хранит список объектов, которые пользователь хочет посмотреть, также с составным уникальным индексом.

## 2.5 Проектирование алгоритмического ядра

### 2.5.1 Алгоритм построения TF-IDF-модели

Контентная модель строится из коллекции `movies` MongoDB. Для каждого объекта формируется текстовое представление с взвешиванием полей:

```
text(d) = title × 3 ⊕ genres × 2 ⊕ overview ⊕ cast ⊕ keywords
```

где символ ⊕ обозначает конкатенацию строк, а умножение -- повторение токенов (реализует частотное взвешивание в рамках TF-IDF без изменения алгоритма). (2.1)

TF-IDF-матрица T ∈ R^(n×v) формируется параметрами: max_features = 50 000 (словарь), ngram_range = (1, 2) (монограммы и биграммы), stop_words = "english". Этот подход соответствует рекомендациям [10].

На рисунке 2.7 представлена блок-схема алгоритма формирования персональных рекомендаций.


### 2.5.2 Алгоритм MMR (Maximal Marginal Relevance)

Алгоритм MMR итеративно отбирает объекты, максимизируя формулу (1.6). Псевдокод алгоритма:

```
Вход: candidates (отсортированные по score), λ, limit
Выход: selected (список объектов с улучшенным разнообразием)

selected ← []
remaining ← candidates

пока |remaining| > 0 и |selected| < limit:
    best_score ← -∞
    best_item ← None

    для каждого item в remaining:
        rel_score ← item.score
        если |selected| = 0:
            mmr ← λ × rel_score
        иначе:
            max_sim ← max(cos(TF-IDF[item], TF-IDF[s]) для s ∈ selected)
            mmr ← λ × rel_score - (1 - λ) × max_sim

        если mmr > best_score:
            best_score ← mmr
            best_item ← item

    selected.append(best_item)
    remaining.remove(best_item)

вернуть selected
```

## 2.6 Проектирование пользовательских сценариев

### 2.6.1 Сценарий онбординга

Онбординг решает проблему холодного старта за минимальное число шагов:
1. После регистрации пользователь перенаправляется на страницу `/onboarding`.
2. Frontend загружает кандидатов через API (параллельные запросы к TMDB: trending + popular + top_rated для фильмов и сериалов).
3. Пользователь выбирает не менее 12 понравившихся объектов из предлагаемой сетки.
4. Бесконечная прокрутка через `IntersectionObserver` подгружает следующие страницы кандидатов.
5. Нажатие «Продолжить» сохраняет выбор через `PUT /api/users/onboarding`, автоматически создавая записи `Rating` с `value = 1`.
6. Пользователь перенаправляется на главную страницу с уже персонализированной лентой.

### 2.6.2 Сценарий взаимодействия через Telegram-бот

1. `/start` -- авторизация по Telegram ID через `BOT_SHARED_SECRET`. При первом подключении запрашивается email для связи аккаунта.
2. Кнопка «Что посмотреть?» -- запрос `/api/recommendations/for-you`.
3. Кнопка «Выбрать настроение» -- показ инлайн-клавиатуры с 7 настроениями.
4. Кнопки лайк/дизлайк -- синхронизация с веб-профилем через `/api/actions/rate`.
5. Кнопка «История» -- последние 5 оценок пользователя.

Ключевое проектное решение: бот не хранит пользовательских данных -- весь профиль в Backend обеспечивает единое пространство данных.

### 2.6.3 Проектирование состояний интерфейса

Для каждой витрины рекомендаций проектируются четыре состояния:

- **loaded** -- горизонтальная строка карточек;
- **empty** -- нулевое состояние с призывом к действию;

### 3.1.2 Middleware-стек

### 3.1.3 Аутентификация и безопасность

JWT-токен формируется с полезной нагрузкой `{userId, email}` и сроком действия `JWT_EXPIRY` (по умолчанию 30 дней). Пароли хэшируются bcrypt с cost factor = 10.

Ниже приведен ключевой фрагмент middleware аутентификации (рисунок 3.2):

```javascript
// src/middleware/auth.js
export function requireAuth(req, res, next) {
  const header = req.headers.authorization ?? '';
  if (!header.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  const token = header.slice(7);
  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET);
    req.user = payload;
    next();
  } catch {
    return res.status(401).json({ error: 'Token invalid or expired' });
  }
}
```

Рисунок 3.2 -- Реализация middleware аутентификации

Для сброса пароля используется одноразовый токен (crypto.randomBytes(32)), хэшируемый SHA-256 перед сохранением в поле `passwordResetTokenHash`. Это исключает хранение токена в открытом виде в базе данных.

### 3.1.4 Кэш рекомендаций

Кэш рекомендаций реализован через `Map<string, {data, expiresAt}>` в памяти процесса. Уникальность ключа гарантируется включением «подписи» рейтингов пользователя:

```javascript
// src/routes/recommendations.js
async function getRatingsSignature(userId) {
  const [count, last] = await Promise.all([
    Rating.countDocuments({ userId }),
    Rating.findOne({ userId }).sort({ updatedAt: -1 }).select({ updatedAt: 1 }).lean(),
  ]);
  const t = last?.updatedAt ? new Date(last.updatedAt).toISOString() : 'none';
  return `${count}:${t}`;
}
```

### 3.1.5 Паттерн «ensureMovie» (upsert)

При выставлении оценки на объект, отсутствующий в локальной базе данных, Backend автоматически запрашивает его метаданные в TMDB API и сохраняет с помощью паттерна `updateOne(..., { $setOnInsert: {...} }, { upsert: true })`. Это гарантирует наличие метаданных для ML-модели при первом же взаимодействии пользователя с объектом.

### 3.1.6 Реализация Watchlist

Сервис Watchlist реализован в `src/routes/watchlist.js` и предоставляет четыре эндпоинта. При добавлении в watchlist объекта, отсутствующего в `movies`, автоматически выполняется обогащение через TMDB API.

### 3.1.7 LLM-переформулировка объяснений

Модуль `src/lib/llm.js` опционально переформулирует шаблонные объяснения рекомендаций через Large Language Model (Ollama / OpenAI). ### 3.2.5 Реализация MMR

Ключевой фрагмент реализации MMR-перераспределения:

```python
# ml-service/app/services/hybrid.py (фрагмент)
def _mmr_rerank(candidates, lambda_mmr=0.7, limit=20):
    model = get_content_model()
    id_to_idx = {mid: i for i, mid in enumerate(model.ids)}
    selected_indices, remaining, result = [], list(candidates), []

    while remaining and len(result) < limit:
        best_score, best_pos = -float("inf"), 0
        for pos, item in enumerate(remaining):
            tmdb_id, rel_score = item[0], float(item[1])
            idx = id_to_idx.get(tmdb_id)
            if idx is None or not selected_indices:
                mmr = lambda_mmr * rel_score
            else:
                sims = cos_sim(model.tfidf[idx], model.tfidf[selected_indices])
                mmr = lambda_mmr * rel_score - (1-lambda_mmr) * float(np.max(sims))
            if mmr > best_score:
                best_score, best_pos = mmr, pos
        chosen = remaining.pop(best_pos)
        if id_to_idx.get(chosen[0]) is not None:
            selected_indices.append(id_to_idx[chosen[0]])
        result.append(chosen)
    return result
```

# 4 Тестирование системы

## 4.1 Стратегия и виды тестирования

Тестирование системы EMZ View проводилось на нескольких уровнях:
1. **Функциональное тестирование Backend API** -- проверка соответствия поведения эндпоинтов спецификации;

```javascript
// backend/src/middleware/auth.js (полный код)
import jwt from 'jsonwebtoken';

export function requireAuth(req, res, next) {
  const header = req.headers.authorization ?? '';
  if (!header.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  const token = header.slice(7);
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    return res.status(401).json({ error: 'Token invalid or expired' });
  }
}
```

```javascript
async function getRatingsSignature(userId) {
  const [count, last] = await Promise.all([
    Rating.countDocuments({ userId }),
    Rating.findOne({ userId })
      .sort({ updatedAt: -1, _id: -1 })
      .select({ updatedAt: 1 })
      .lean(),
  ]);
  const t = last?.updatedAt
    ? new Date(last.updatedAt).toISOString()
    : 'none';
  return `${count}:${t}`;
}
```
